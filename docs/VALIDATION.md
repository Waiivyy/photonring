# Validation

Every check from the project brief (section 10), its tolerance and its measured result, then the
checks added later. Machine: Apple M5 (10-core GPU), macOS 27.0, Node 25.6.1; browser checks in
headless Google Chrome 156 through Playwright (156.0.8078.48, recorded by the benchmarks of
2026-10-27 and 2026-10-28 and at the first Stage 6 re-run of the GPU tests, and 156.0.8078.74 at
the second; the Stage 2 benchmark of 2026-10-26 recorded 156.0.8078.47, and other earlier runs
only the major version). "f32" in Node-side rows means the `Math.fround` emulation.

Where the measured values come from:

- **Node-side rows whose "Where" names `npm run measure`.** That command runs the Vitest suites
  with `MEASURE=1`. The analytic, integrator, camera, contrast, raytrace, lensing,
  overlay-geometry, star field, numerics and colour tests pass the values these rows give through
  `measured()` (`tests/helpers/measured.ts`), and `tools/measured-report.ts` prints the worst
  value of each recorded check: its key, the value, whether the largest or the smallest counts,
  and the test file. It prints no tolerances; they are in the tables below. The values below are
  its output at commit 8c374bd (2026-11-02), rounded to two significant digits unless more are
  meaningful. Other Node-side values are from the run that added the check.
- **GPU rows.** The logs of `npm run test:gpu` (WGSL, f32, on the M5's GPU), first measured from
  Stage 2 to Stage 5 (2026-10-26 to 2026-10-28), then re-run at commit 0123428 (2026-10-28,
  Chrome 156.0.8078.48) and at commit afd9fd5 (2026-11-02, Chrome 156.0.8078.74), all 14 tests
  passing both times. Every value both re-runs logged equals the one given here; the overlay row's
  0.01 px and 0.75 px come from a one-off run at Stage 4 and are not logged.
- **The CPU shadow table** comes from `npm run render:cpu`, the Stage 0 integrator comparison from
  `npm run spike` (`docs/DESIGN.md`, section 3).

"Pass" stands where a test checks an exact result or a yes/no property (identical bytes, a sign,
a classification, a bracket, never throwing). "Bound held; value not recorded" marks the few
checks with a numeric bound whose test does not record the value: the two page checks run by
Playwright (the Validation panel and the overlays in the page) and the ring solver's tiny sweeps.

`npm test` runs the Vitest suites (unit, property and golden tests); `npm run test:gpu` the GPU
rows; `npm run test:e2e` (dev server) or `npm run test:e2e:build` (the build, with its CSP) the
page rows; `npm run test:dist` item 15. CI runs the same browser tests on GitHub's runners
(`docs/DESIGN.md`, sections 5 and 14): the GPU tests and the page tests against the build on
macos-15 with Chrome 152 on the runner's GPU, item 15 and the 14 smoke tests on ubuntu-24.04 with
Chrome 155 or 156 on SwiftShader. In the first 17 CI runs on 2026-10-28, the 13 GPU tests of
Stage 5 and the 109 page tests against the build passed on macos-15 in all 13 runs in which GitHub
started the job.

## Tolerance changes

- **Blackbody chromaticity at 1500 K: 0.002 to 0.005** (Stage 1). The analytic colour-matching
  fit deviates most from the CIE table in the red tail, which dominates a 1500 K spectrum; the
  measured offset is 0.0046 in x and y. All other temperatures keep 0.002.
- **sRGB continuity at the knee: $10^{-9}$ to $10^{-7}$** (Stage 1). The standard's two pieces
  meet only to about $3\times10^{-8}$ at 0.0031308, a property of the standard, not of the code.
- Two Stage 1 test assumptions were wrong rather than loose and were corrected: hue order is
  checked in XYZ because deep-red blackbodies are outside the sRGB gamut, and the tone curve
  equals 1 to f64 precision at large inputs.
- **GPU crossing radii compared only up to twice the outer disk radius** (Stage 3, new test). The
  first version compared every crossing radius at $10^{-4}$ and measured $1.4\times10^{-4}$ for
  crossings near $10^4M$, where $u = 1/r$ is close to 0 at escape and f32 keeps less relative
  precision. Such crossings can never land on the disk. Radii up to $2r_{out}$ keep $10^{-4}$
  (measured $3.4\times10^{-5}$); farther ones are logged.
- **Disk temperature closed form: $10^{-14}$ to $10^{-11}$** (Stage 3, new test). Near $r_{in}$
  the factor $1 - x^{-1/2}$ cancels ($8\times10^{-5}$ at $r = 6.001M$), which amplifies rounding
  differences between two algebraically identical forms.
- **No Stage 4 accuracy tolerance was loosened.** One was tightened: the ISCO overlay against the
  GPU disk edge was first checked at 0.5 px for every 8th vertex, on and off screen; it is now
  0.05 px for every 4th on-screen vertex, after the one-off measurement above.
- **Off-screen overlay vertices: budget raised by 248** (Stage 4). The vertex budget in
  `tests/unit/overlay-geometry.test.ts`, written before the code (8852020) as
  `BASE_SAMPLES + 2 * 8 * segments + 8`, became `2 * BASE_SAMPLES + 16 * segments` with the curve
  builder (1de1545): off screen, each interval of the base sampling gets its midpoint, to see
  whether the curve comes back on screen, but no recursive refinement. With `BASE_SAMPLES = 256`
  that allows 248 more off-screen vertices. This is a budget, not an accuracy bound; the on-screen
  bounds are unchanged.
- **No tolerance was loosened in Stage 5.** Two harness settings are new and only affect the
  browser tests: in CI the page tests retry once, so a page test that fails once and then passes
  leaves the job green (the offline test never retries, and the GPU parity step fails on any
  retry); with the SwiftShader adapter, assertions wait up to 60 s instead of 5 s.
- **No tolerance changed in Stage 6.** Tests gained cases: the integrated deflection now spans
  1.01 to 1000 $b_c$, as item 2 asks (it covered 1.02 to 100), and the GPU readback is checked for
  non-finite values (item 10, `tests/gpu/robustness.spec.ts`). Ten Vitest files now record the
  values that the rows citing `npm run measure` give (commits 0ff1b63 and 8c374bd); every bound
  stayed as it was.
